- 작성일 2026-11-26 · 기준: 작업 폴더 코드+ 2026-11-06 실측 기록
- 이 폴더(`docs/프로젝트_전체_가이드/`)는 **다른 문서 없이 이것만 읽어도** 프로젝트를 넘겨받을 수 있게 만든 자기완결 가이드입니다. 읽는 순서는 `00_README_읽는순서.md`.

## 1. 이 프로젝트는 무엇인가

병원·관공서·주차장에서 손님을 목적지까지 걸어서 데려가는 **4족(바퀴 달린 다리) 보행 안내 로봇 "큐리"**(제조사 M20 계열)와, 이 로봇을 지도·일정·음성 시나리오로 움직이는 **관제 시스템**입니다.

할 수 있는 일:

| 기능 | 한 줄 설명 |
|---|---|
| 관제 화면 | 로봇 위치·배터리·영상 보기, 지도·장소·경로 편집, 작업(일정) 등록, 알림·로그·통계·녹화 |
| 안내 시나리오 | 병원(`hospital`)·관공서(`public_office`)·주차장(`parking`) 안내를 단계(말하기→듣기→판정→이동)로 진행 |
| 상시 대기 | 대기 장소에서 근무하다 "큐리야"라고 부르면 응대 → 안내 → 복귀 |
| 자율 이동 | 노드망(맵 위 점·선)으로 경로를 계산하고, 여러 지점을 한 묶음으로 로봇에 전송 |
| 층 이동·자동문 | 엘리베이터는 사람이 태워 주는 방식(수동 맵 전환), 자동문은 통과 게이트 코드가 있으나 일부 미배포 |
| 충전 | 배터리 부족 시 자동 충전소 복귀·도킹, 충전 후 이어 가기 |

## 2. 구성 요소(저장소 폴더)와 실제 실행 위치

> **가장 중요한 사실: 작업 폴더 ≠ 실행본.** 저장소에서 파일을 고쳐도 로봇은 바뀌지 않습니다. 장비마다 정해진 배포를 거쳐야 반영됩니다.

| 구성 | 저장소 폴더 | 스택 | 실제로 도는 곳 |
|---|---|---|---|
| 관제 백엔드 | `Backend/` | FastAPI, Python 3.10, SQLAlchemy + PyMySQL, OpenCV, FFmpeg | **관제 PC**의 도커 `control-backend` (8010) |
| 관제 화면 | `Frontend/` | Next.js 15(정적 export), React 18, TypeScript, Tailwind 4, Three.js | 관제 PC 도커 `control-frontend` (3001, nginx) |
| DB | `db/`(덤프) | MariaDB 10.11 | 관제 PC 도커 `control-db` (호스트 3307→3306), 또는 `DATABASE_URL` 로 지정한 외부 DB |
| 영상 중계 | `MediaMTX/` | MediaMTX(RTSP→WebRTC) | 관제 PC 도커 `control-mediamtx` (8889, 8189/udp) |
| 사람 인식 | `robot_vision/` | YOLOv8 | 관제 PC 도커 `control-vision` |
| 로봇 로그 수집 | `tools/robotlog/` | Python | 관제 PC 도커 `control-robotlog` |
| 로봇 중계기 | `robot_receiver/` | Python 3 표준 라이브러리 + ROS2(rclpy) | **NOS 보드** `/home/user/Control_system/` |
| 음성 안내 | `robot_voice/` | Python, OpenAI(합성·판정), faster-whisper(로컬 인식) | **Jetson** `/opt/robot/voice/robot_voice` |
| 사전 시뮬 | `sim/` | Python 가상 시계 + 가짜 로봇 | 작업 PC |

**관제 PC는 특정 장비로 정해져 있지 않습니다.** 저장소를 받아 도커(compose)를 띄운 PC(휴대용·데스크톱·서버 등 종류와 무관)가 곧 관제 PC입니다. 같은 코드라도 어떤 compose 파일로 띄우느냐, 어떤 OS 이냐에 따라 도는 환경이 달라집니다.

| 띄우는 방식 | 컨테이너 네트워크 | 로봇망 접근 |
|---|---|---|
| `docker-compose.local.yml` | backend 가 bridge | 호스트 PC 에 로봇망(10.21.31.0/24) 경로가 있어야 함 |
| `docker-compose.windows.yml` | bridge, `db/init/` 덤프 자동 import | 위와 같음 |
| `docker-compose.linux.yml` | backend 가 host 네트워크 | 로봇·중계기와 직접 UDP·TCP |

- 이 가이드에 적힌 주소(172.30.1.58 등)와 구성은 **2026-11 시점에 실제 운영하던 관제 PC 한 대**의 기록입니다(그 PC 는 이동형이라 로봇과 함께 층을 옮겨 다녔습니다). 다른 PC 에 옮겨 띄우면 **주소·로봇망 경로·방화벽·포트 예약은 그 PC 기준으로 다시 설정**해야 합니다(`02_네트워크_포트_장비.md` 4절, `08_설정_환경변수_배포.md` 4절).
- `.env` 의 `COMPOSE_FILE` 과 배포 명령의 compose 파일 이름·프로젝트명은 **작업하는 PC 기준**입니다. 이 가이드의 명령 예시는 `docker-compose.local.yml`, 프로젝트명 `und-control` 을 쓰므로, 다른 PC 에서는 그 PC 에서 실제로 쓰는 값으로 바꿔 쓰세요(`08_설정_환경변수_배포.md` 1·3절).

근거: `docker-compose.local.yml`·`windows.yml`·`linux.yml`(서비스 db·backend·mediamtx·vision·robotlog·frontend, 컨테이너 이름, 네트워크 방식), `README.md`, `Frontend/package.json`.

"로봇"은 실제로 **본체·NOS 보드·Jetson** 세 장비의 묶음이고, 여기에 **관제 PC**(도커를 띄운 PC, 2절 참고)가 더해집니다.

| 장비 | 주소(2026-11-06 기록) | 하는 일 |
|---|---|---|
| 관제 PC | 층 Wi-Fi 172.30.1.58 (당시 운영 PC 기록 — PC 가 바뀌면 달라짐) | 도커 6개 실행. 지도·장소·경로·일정·안내 시나리오 관리. 로봇 위치·상태를 계속 묻고 이동 명령을 보냄 |
| 로봇 본체 | 10.21.31.103 (로봇 내부망) | 제조사 M20 보행 제어·주행 서버(`basic_server`). 제조사 명령 규약(ASDU) UDP 30000 · TCP 30001. 전방 카메라 RTSP 8554. 로그 `/var/opt/robot/log` |
| NOS 보드 | 10.21.31.106 (로봇 내부망) | 제조사 측위(지도 매칭)·라이다·경로 계획(ROS2 **Foxy**). **우리 중계기 `receiver.py`**가 관제 명령을 받아 본체로 전달. 보조 노드: 지도·충전·보행 중계, 장애물 감지 |
| Jetson | 172.30.1.44(Wi-Fi) · 10.21.31.10(유선) | 음성 안내(마이크 reSpeaker XVF3800, 스피커 UACDemo, 호출어 "큐리야"). Jetson 안 음성 인식 서버(8091). 층 Wi-Fi와 로봇 내부망을 잇는 **관문(주소 변환)** |

## 4. 시스템 구조도

```
┌──────────── 관제 PC (도커 프로젝트 und-control) ────────────────┐
│                                                                  │
│   운영자 브라우저 ──화면──▶ frontend :3001                       │
│        │                        │ API 호출                       │
│        │ 영상(WebRTC)           ▼                                │
│        ▼                   backend :8010 (FastAPI) ◀──▶ db :3307→3306 (MariaDB)
│   mediamtx :8889                │                                │
│        ▲ 원본 영상              │          vision(사람 인식)  robotlog(로그 수집)
└────────┼────────────────────────┼────────────────────────────────┘
         │ RTSP 8554              │ 위치·상태 묻기 / 이동 명령
         │                        │ UDP 40000 · TCP 40001
         │                        ▼
         │      ┌──────────── NOS 보드 10.21.31.106 ─────────────┐
         │      │  중계기 receiver.py  (JSON ↔ ASDU 변환)         │
         │      │     ▲ 지도 50000·충전 50001·보행 50002/50003(내부 전용)
         │      │     ▲ 장애물 감지 노드 UDP 40100 → 정지 요청     │
         │      │  제조사 측위·계획기 (ROS2 Foxy·라이다)          │
         │      └───────────────┬─────────────────────────────────┘
         │                      │ ASDU 명령·응답 (UDP 30000 / TCP 30001)
         │                      ▼
         └──────────── 로봇 본체 10.21.31.103
                       보행·주행 실행, 배터리·관절 온도·충전 상태 보고

  Jetson 172.30.1.44 / 10.21.31.10
    robot-voice: 듣기 → 판정 → 말하기, 시나리오 단계 진행
    stt-server :8091 (Jetson 안 음성 인식) · OpenAI(합성·판정)
    ──▶ backend :8010  음성 시나리오·세션 HTTP (주기 호출, X-Agent-Token)
    ──▶ receiver UDP 40000  앉아·일어서 (상시 대기 '단순 동작' 응대, 전시용)
```

핵심 규칙:
- 관제 백엔드는 본체와 **직접 이야기하지 않고 언제나 NOS 중계기를 거칩니다** (`Backend/app/robot_io/polling.py` 가 `RECEIVER_IP:RECEIVER_PORT` 로 보냄).
- 이동 명령은 TCP 우선, 실패 시 UDP (`Backend/app/robot_io/sender.py`).
- 본체는 이동 중 새 이동 명령을 거부하므로 여러 지점은 **한 묶음으로 보냅니다**(최대 5점).
- 현재 코드는 **로봇 1대 전제**입니다. 통신 대상 주소가 전역 `RECEIVER_IP`/`ROBOT_IP` 하나입니다(`robot_io/polling.py:380-389`, `robot_io/sender.py:95-96`). DB·런타임 상태는 여러 대를 담도록 만들어져 있으나(`runtime.init_runtime(all_robots,…)`) 폴링·명령 경로는 한 대입니다.

## 5. 대표 흐름 두 가지

### 평소: 로봇 상태가 화면에 뜨기까지
1. 관제 백엔드 조회 스레드가 NOS 중계기(UDP 40000)에 `POSITION`·`STATUS`·`NAV_STATUS`를 계속 묻습니다.
2. 중계기가 본체(ASDU 30000)에 물어 위치·배터리·주행 상태를 받고, 측위·충전·보행 정보를 보조 노드에서 합쳐 돌려줍니다.
3. 백엔드는 메모리에 로봇 상태를 두고 30초마다 DB(`robot_last_status`)에 저장합니다. 응답이 끊기면 "통신 두절" 알림을 냅니다.
4. 화면이 백엔드 API를 주기적으로 불러 지도 위 로봇 마커·카드를 갱신합니다. 영상은 영상 중계(8889)에서 따로 받습니다.

### 안내 한 건: 손님을 목적지까지
1. 운영자가 화면에서 안내를 시작하거나, 대기 중인 로봇에게 손님이 "큐리야"라고 부릅니다.
2. 백엔드가 안내 세션(`service_session`)을 열고, Jetson 음성이 세션·시나리오를 받아 단계를 진행합니다(묻기 → 듣기 → 판정).
3. 목적지가 정해지면 Jetson이 백엔드에 이동을 요청(`/move`)하고, 백엔드가 노드망 경로를 계산해 여러 지점을 한 묶음으로 중계기에 보냅니다.
4. 중계기가 본체에 주행 명령을 넣고, 이동 중 백엔드가 방향 안내·진행 멘트 시점을 계산하면 Jetson이 말합니다.
5. 도착을 판정하면 도착 멘트, 다음 단계(창구 번호 안내, 층 이동 등)로 넘어가고, 끝나면 대기 장소로 돌아갑니다.

단계별 상세·예외는 `07_핵심_동작_흐름과_예외처리.md`.

## 6. 작업 폴더와 실행본이 다른 이유와 확인 방법

| 구성 | 실행본 위치 | 설정 | 상태 확인 방법 |
|---|---|---|---|
| 관제 | 관제 PC 도커 이미지 | 루트 `.env` (compose 환경 변수 목록에 있어야 전달) | 컨테이너 안 파일 해시·`docker compose ps`·환경 변수 조회 |
| NOS 중계기 | NOS `/home/user/Control_system/receiver.py` | systemd 서비스 파일·추가 설정 | `robot_receiver/tools/nos_receiver.py check` |
| Jetson 음성 | `/opt/robot/voice/robot_voice` | `/etc/robot-voice.env` (관제 화면의 "음성 튜닝값"은 Jetson이 사용하지 않음, 06번 문서 2-2절) | 내 PC·`/home/und02/project`·`/opt` 해시 대조 |

상태(배포 여부·설정값)는 **메모가 아니라 실행 중인 환경**에서 확인합니다. 배포 절차는 `08_설정_환경변수_배포.md`.

## 7. 앱 시작 순서(백엔드)

`Backend/app/main.py` 기준:

1. 모듈 임포트 시점에 `start_polling_threads()`(로봇 조회 스레드)가 시작됩니다(`main.py:335`).
2. FastAPI `startup`: 테이블 생성(`Base.metadata.create_all`) → 매핑 TCP 서버 → 기본 데이터 시드·스키마 보정(`seed_all`) → 사용자·로봇 캐시 → 로봇 런타임 초기화(DB 마지막 상태 복원).
3. 부팅 시 고착된 `IsWorking`(작업 중) 플래그 정정 → 로봇 소유권 초기화(`cluster`, `control_lock`) → **고아 스케줄·회차 복구** → 충전 후 이어가기 분실 알림.
4. 스케줄러 스레드(`scheduler_thread`), 안내 세션 정리 감시, FFmpeg 확인·녹화 고아 정리·보관 정책 스레드, 로봇 상태 저장 스레드(`persistence`), 맵 파일 DB↔로컬 동기화·맵 이미지 백필(백그라운드).
5. 마지막에 `system_startup` 로그를 남깁니다.
6. 종료 시 폴링·매핑 루프에 종료 신호, 상태 저장, 녹화 정지.

> 스키마 변경은 별도 마이그레이션 도구 없이 **`seed.py` 안의 `migrate_*` 함수(ALTER TABLE, 멱등)** 로 처리합니다. 그래서 스케줄러는 `seed_all` 이후에 켜야 합니다(`main.py:210-211` 주석). 칸 삭제·이름 변경과 이력 관리가 필요해지면 Alembic 같은 도구를 검토할 수 있습니다.

## 8. 개발 방식 요약(상세는 09번)

- 기능 변경은 먼저 `sim/` 가상 시뮬로 현행 vs 변경 결과를 보고 승인받은 뒤 작업 폴더에 반영합니다(`presim` 절차).
- 배포는 08번 문서의 절차(사전 점검 → 승인 → 실행 → 사후 확인 → 되돌리기)대로, 한 번에 한 사람이 합니다.
- 시험은 반드시 **관제를 거쳐서만** 합니다(제조사 앱·직접 스크립트 주행은 결과가 무효이거나 오경보).
