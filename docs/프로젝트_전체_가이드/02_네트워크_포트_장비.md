## 6. 통신 규약 요약

| 구간 | 프로토콜 | 비고 |
|---|---|---|
| 화면 ↔ 백엔드 | HTTP/JSON(쿠키 JWT), WebSocket(맵핑·재조정) | 개발 시 `next.config.js` 프록시로 8010에 붙음 |

## 7. 장비 시계(시각) 차이

여러 장비의 로그를 시각으로 맞춰 볼 때 가장 먼저 부딪히는 문제입니다. 장비마다 시계가 달라서, 같은 순간이 로그마다 다른 시각으로 찍힙니다.

| 장비 | 관제 PC 시각과의 차이 | 비고 |
|---|---|---|
| 로봇 본체 | 약 25~34초 빠름 | 9~10월 기록 |
| NOS | 약 58~115초 빠름 | 10월 기록. 날마다 달라서 고정 값으로 쓸 수 없음 |
| 관제 백엔드 도커 로그 | 시각이 **세계 표준시(UTC)** 로 찍힘 | 한국 시각보다 9시간 늦게 보임 |
| Jetson | 신뢰할 수 없음 | RTC(시계 배터리)가 없어 켤 때마다 틀어질 수 있음. 관제 HTTP 시각으로 맞추는 서비스가 있으나(`robot_receiver/setup_timesync.sh`) 로그 비교에는 쓰지 않음 |

**로그를 맞춰 보는 방법**
1. 같은 사건이 양쪽 로그에 모두 찍히는 지점을 찾습니다. 가장 쓰기 좋은 것은 **이동 명령을 보낸 시각(관제)과 받은 시각(중계기·본체)** 입니다.
2. 두 시각의 차이를 그날의 오차로 정하고, 나머지 로그를 그만큼 보정합니다. 오차는 날마다 달라지므로 그날 다시 구합니다.
3. **1초 이하 타이밍**(예: 멈춤 지연, 출발 지연)은 관제 로그로는 정확히 알 수 없으니 **로봇 본체 로그**로 봅니다.

**코드에 미치는 영향:** 중계기가 보고한 STATUS 시각과 관제 시각을 직접 비교해 "오래된 값인지" 판정하는 곳이 있습니다(`Backend/app/robot_io/polling.py:555-558`). 두 장비의 시계가 크게 어긋나면 정상 값을 오래된 값으로 오판할 수 있습니다(추정).

## 8. Windows 환경에서 겪는 문제

관제 PC를 Windows 로 운영할 때 반복해서 만난 문제 세 가지입니다.

### 8-1. 컨테이너는 떠 있는데 포트에 접속이 안 될 때
- **증상:** `docker ps` 에서 컨테이너는 `Up` 인데 화면(3001)이나 백엔드(8010)에 접속할 수 없음. PC 재부팅 뒤에 나타난 적이 있음(10-14, 10-20).
- **먼저 볼 것:** 관리자 터미널에서 `netsh int ipv4 show dynamicport tcp` 를 실행해 **시작 포트(Start Port)가 49152 인지** 확인합니다.
- **원인:** 시작 포트가 1024 로 바뀌어 있으면 Windows 의 NAT 서비스(WinNAT)가 3001 같은 포트를 임시 포트로 선점해 컨테이너가 쓰지 못합니다.
- **조치:** 시작 포트를 49152 로 되돌리고 WinNAT 를 재시작합니다. 당시 기록은 "49152 로 복구, winnat 재시작"입니다. 복구 명령은 Windows 표준 형식으로 `netsh int ipv4 set dynamicport tcp start=49152 num=16384`(관리자 권한)입니다.

### 8-2. Git Bash 에서 명령을 실행할 때
- 컨테이너 안 경로를 인자로 넘기면 Git Bash 가 Windows 경로로 바꿔 버립니다. 명령 앞에 `MSYS_NO_PATHCONV=1` 을 붙입니다. 예: `MSYS_NO_PATHCONV=1 docker exec control-backend ls /app/data`
- 한글 출력이 깨지면 `PYTHONIOENCODING=utf-8` 을 붙입니다. 예: `PYTHONIOENCODING=utf-8 python <스크립트>`

### 8-3. 한글이 들어간 `.bat` 파일
- 한글이 깨지지 않도록 **첫 줄에서 UTF-8 코드 페이지로 바꿉니다**(`chcp 65001`, 예: `logs.bat`). 새 bat 를 만들 때도 같은 방식을 따릅니다.
- 문자열 안에 `!` 가 있으면 의도와 다르게 해석될 수 있으니 주의합니다.
