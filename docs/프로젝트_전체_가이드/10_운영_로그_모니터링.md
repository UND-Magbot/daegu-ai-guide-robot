## 2. 관제 DB 로그 (`logdata_info`, 화면: 데이터 관리 › 로그)

| 칸 | 형식 | 내용 |
|---|---|---|
| id | 정수, 자동 증가 | 로그 번호 |
| Category | 문자열 20자 | 분류. 모델 주석은 robot / system / schedule / error (`models.py:69`) |
| Action | 문자열 50자 | 이벤트 이름표(3절) |
| Message | 문자열 500자 | 사람이 읽는 한 줄 설명 |
| Detail | 글(JSON 문자열) | 상세 정보 |
| RobotId / RobotName | 정수 / 문자열 100자 | 대상 로봇 |
| BusinessId | 정수 | 사업장. system 로그는 NULL |
| CreatedAt | 날짜시각 | 기록 시각(DB 기본값) |

화면 응답(`schemas.py`)은 BusinessId 를 뺀 칸 + 목록 응답 `items, total, page, size, earliest_date`.

### 2-1. 조회·기록 규칙
- 조회 `GET /DB/logs`: 조건 `category`, `search`(Message 포함), `start_date`, `end_date`, `page`, `size`(1~10000), 최신순. 로그 권한(`require_permission("log")`)이 필요하고, 최고 관리자가 아니면 자기 사업장 로그만 봅니다.
- `robot_online`/`robot_offline` 은 저장되지만 **목록 조회에서 제외**(통계용).
- 기록 `log_event(category, action, message, detail, robot_id, robot_name, error_json, business_id)`: 큐(크기 500)에 넣고 **전용 스레드 하나가 DB 에 기록**합니다.
  - 같은 Action 이 **30초 안에 반복되면 기록하지 않고** 다음 로그에 "(이전 N건 동일 로그 생략됨)"을 붙입니다. 예외 목록 `_COOLDOWN_EXEMPT`(`service.py:19`)의 Action(nav_arrival·schedule_*·guide_*·standby_*·battery_resume_* 등)은 매번 기록.
  - 큐가 가득 차면 새 로그를 버립니다(`queue.Full`).
  - DB 기록이 실패하면 DB 가 아니라 컨테이너 출력에 `[ERR log_writer]` 만 남습니다.
- **값 검사 없음:** Category·Action 은 길이만 제한된 자유 문자열입니다. 모델 주석의 목록은 설명용. 변수로 넘기는 호출이 있어(아래 4절) 4가지 밖의 Category 가 있을 수 있습니다(추정).
- 알림 연동: `ALERT_TRIGGER_RULES`(`service.py:55`)에 등록된 Action 은 `alert_info` 도 함께 만듭니다(Type: Robot/Schedule, Status: error/event, 제목·상세·ErrorJson·LogId). **Robot 타입 알림은 해당 로봇이 오프라인이면 만들지 않고**(로그는 남음), 스케줄 계열은 오프라인이어도 알림이 나가도록 Schedule 타입을 씁니다(스케줄 실패의 상당수가 오프라인이 원인). 로봇 에러 코드는 온라인일 때만 들어오므로 항상 생성.

## 5. 알림(Alert) 체계

- 테이블 `alert_info`(+ `alert_read_status` 읽음), API `/DB/alerts`(목록·상세·읽음·전체 읽음·안 읽은 수), 화면 "알림" 탭(전체·스케줄·로봇·공지사항)과 전역 팝업 감시자(`05_프론트엔드_구조.md` 4절).
- 알림 유형: `Robot`(로봇 오프라인이면 억제) / `Schedule`(항상) / 공지 생성 시 알림.
- **"조용한 실패 금지" 원칙:** 스케줄 실패·응대 실패·통신 두절·배터리 부족·측위 실패 같은 운영자가 개입해야 하는 상황은 반드시 알림이 나가야 합니다(쿨다운 예외 목록이 그 이유). 새 실패 경로를 만들면 Action 을 `ALERT_TRIGGER_RULES` 에 넣고 필요하면 `_COOLDOWN_EXEMPT` 에도 넣으세요.

## 6. 모니터링·상태 확인 방법

| 알고 싶은 것 | 보는 곳 |
|---|---|
| 컨테이너가 떴나 | `docker compose -f docker-compose.local.yml -p und-control ps` |
| 백엔드 살아있나 | `GET :8010/api`(200), `/robot/status`(로그인 없이 **401** 이 정상) |
| 화면 | `:3001/`(200) |
| 로봇 통신 | 화면 서버 건강 배너(`ServerHealthBanner`), `/robot/status` 의 응답·age, 로그 `robot_connection_error`/`robot_offline`/`receiver_unresponsive` |
| 로봇이 어디에 있나 | 대시보드 지도, 측위 기록 `backend_logs/loc_trace/`, 위치 급변·측위 상실 알림 |
| 한 안내가 왜 안 풀렸나 | `service_session`(Result·ClosedBy·CurrentStepCode), 로그 `guide_*`·`nav_*`, Jetson journal |
| NOS 중계기·장애물 감지 | `nos_receiver.py status`·`guard-status`(08번 문서 3-2) |
| 영상 | MediaMTX 상태 API(`127.0.0.1:19997`), 화면 "마지막 화면 N초 전" 배지 |
| 모터 온도 | 로그 `motor_overheat_*`, 상세는 로봇 상세 화면 |
| 저장 공간 | 로그 `storage_warning`/`storage_critical`, 녹화 7일 보존 |

- 화면 통계(데이터 관리 › 통계): 가동·충전·작업·에러 집계, 응대 세션 1건 = 길 안내 1건으로 대시보드 통계·일정에 합산(상시 대기 근무 자체는 안 셈, 실패 응대 = 오류).
- 시간 비교는 장비 시계 차이(본체 +25~34초, NOS +58~115초, 백엔드 로그 UTC)를 보정합니다(`02_네트워크_포트_장비.md` 7절).
