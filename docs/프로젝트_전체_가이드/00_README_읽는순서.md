## 3. 한 장 요약

- **무엇:** 병원·관공서·주차장에서 손님을 목적지까지 데려가는 4족(바퀴형) 보행 로봇 "큐리"와, 지도·일정·음성 시나리오로 이를 움직이는 관제 시스템.
- **구성:** 관제 PC 도커(화면 3001 + 백엔드 8010 + DB + 영상 중계 + 비전 + 로그 수집) → **NOS 보드의 중계기**(UDP 40000/TCP 40001) → 로봇 본체(ASDU 30000/30001). 음성은 **Jetson**이 맡고 관제와 HTTP 로 시나리오·세션을 주고받음. Jetson 은 층 Wi-Fi ↔ 로봇 내부망의 관문.
- **절대 잊으면 안 되는 것 5가지**
  1. 저장소를 고쳐도 로봇은 안 바뀐다 — 장비별 배포가 필요하고, 상태는 **실행 중 환경**에서 확인한다.
  2. 코드 수정은 먼저 사전 시뮬(presim) → 승인 → 반영, 배포는 08번 문서의 절차대로 한 번에 한 사람이 한다.
  3. `.env` 에 넣은 값은 compose 환경 변수 목록에도 있어야 적용된다.
  4. 장소 칸 이름 `LacationName`(오타)이 정본이고, 운영 중 장소 이름 변경·재생성은 금지. 지도를 다시 만들면 번호가 바뀐다.
  5. 커밋은 작업 단위로 경로를 지정해 나누고, 비밀값 파일(`.env*`, `Backend/data/_*.py`, `robot_vision/thermal.env`)은 커밋에서 제외한다. 계정·비밀번호는 코드·설정 파일에 직접 쓰지 않는다(저장소가 공개).

## 4. 갱신 규칙

- 작업을 하나 마칠 때마다 같은 날 함께 고칩니다.
  - 새 문제 → 11 에 한 줄 추가(분야 머리글자 + 다음 번호)하고 맨 위 해결 여부 표에도 올림
  - 상태가 바뀜(배포·실기 확인·커밋) → 11·12 의 해당 칸과 기록일 수정, 11 의 해결 여부 표에서 줄을 옮김
  - 새 할 일·결정 대기 → 12 에 한 줄
  - 구조·설정·절차가 바뀜 → 해당 번호 문서(03·05·06·08 등)
- 내용은 짧게, 틀린 줄은 지우지 말고 "정정:" 을 붙여 남깁니다.
- 비밀번호·토큰은 쓰지 않습니다(변수 이름만).
- 문서 안 줄 번호는 코드가 바뀌면 어긋나므로, 중요한 판단 전에는 해당 파일을 다시 열어 확인합니다.
