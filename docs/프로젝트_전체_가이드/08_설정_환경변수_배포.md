# 08. 설정·환경 변수·배포

- 작성일 2026-11-26 · 근거: `.env.example`, `docker-compose.*.yml`, `robot_receiver/tools/nos_receiver.py`, `README.md`.
- 배포는 되돌리기 어렵고 운영 중인 로봇에 영향을 줍니다. **사전 점검 → 승인 → 실행 → 사후 확인 → 되돌리기 준비** 순서로 합니다(3절).

## 1. 실행 구성(compose) 3종

| 파일 | 용도 | backend 네트워크 |
|---|---|---|
| `docker-compose.local.yml` | **2026-11 기준 운영 PC 가 쓰던 구성**(프로젝트명 `und-control`) | bridge |
| `docker-compose.windows.yml` | Windows 신규 PC 배포. `db/init/` 덤프 자동 import·헬스체크 | bridge — 호스트에 로봇망 라우트 필요 |
| `docker-compose.linux.yml` | Linux 신규 PC 배포 | host — 로봇/중계기와 직접 UDP·TCP |

서비스(local 기준): `db`(mariadb:10.11, `control-db`), `backend`(`./Backend` 빌드, `control-backend`), `mediamtx`(`control-mediamtx`), `vision`(백엔드 이미지 재사용, `control-vision`), `robotlog`(백엔드 이미지 재사용, `control-robotlog`), `frontend`(`./Frontend` 빌드, `control-frontend`).

- backend 볼륨: `./Backend/data`, `./Backend/static`, `./backend_logs`, `./Backend/recordings`(녹화는 컨테이너 재생성 때 사라지던 문제를 11-03 에 볼륨 연결로 수정).
- `.env` 의 `COMPOSE_FILE` 로 기본 대상을 정하면 `-f` 없이 `docker compose` 와 `start.bat`/`stop.bat`/`logs.bat` 을 그대로 씁니다. 2026-11 운영 PC 는 `docker-compose.local.yml`, `.env.example` 기본값은 windows 입니다.
- 기동: `docker compose up -d --build` (Windows 는 `start.bat` — 기동 + 백엔드 healthy 대기). 종료: `stop.bat`(DB 보존) / `stop.bat --clean`(**DB 볼륨까지 삭제 — 운영에서 금지**). 로그: `logs.bat [서비스]`.
- 이미 운영 중인 PC 에서 서비스 일부만 다시 빌드: `docker compose -f docker-compose.local.yml -p und-control up -d --build --no-deps backend frontend`.
- 외부 DB: `.env` 에 `DATABASE_URL` 을 넣고 내장 db 없이 `up -d --no-deps backend mediamtx frontend`. 스키마명은 `APP_ENV` 와 짝(prod=`control_system`, dev=`control_system_dev`).

## 2. 환경 변수 체계 (`.env` → compose `environment:` → `Backend/app/robot_io/config.py`)

> **핵심 함정: `.env` 에 적는 것만으로는 컨테이너에 전달되지 않습니다.** compose 에 `env_file` 설정이 없어서 `.env` 전체가 들어가지 않고, backend 의 `environment:` 목록에 `- 키=${키:-기본값}` 형태로 적힌 키만 전달됩니다.
>
> - **값이 흐르는 길:** `.env` → compose 가 `${키}` 를 치환 → 컨테이너 환경 변수 → `robot_io/config.py` 가 `os.environ` 으로 읽음.
> - **목록에 없을 때의 증상:** `.env` 에 `true` 로 적어도 코드는 기본값(대부분 "꺼짐")으로 동작합니다. 오류나 경고가 나지 않아 "켰는데 안 먹는다"로만 보입니다. 기능 스위치(`NAV_MULTIPOINT_ENABLED`, `NODE_ROUTING_ENABLED` 등)에서 여러 차례 반복된 실수입니다.
> - **예방:** 새 키는 아래 "새 환경 변수를 추가할 때 함께 고칠 곳 4곳"을 한 번에 고치고, 아래 대조 명령으로 빠진 키가 없는지 확인합니다.
> - **적용 확인:** 컨테이너를 다시 띄운 뒤 `docker exec control-backend printenv <키>` 로 값이 들어갔는지 봅니다(비밀값 키는 제외).

- **코드 기본값은 대부분 "꺼짐"**이고, 운영 `.env` 가 켭니다(`robot_io/config.py:148,180,217-251`). 2026-11-06 기준 운영 스위치: `NODE_ROUTING_ENABLED=true`, `NODE_NAV_MODE=auto`, `NAV_MULTIPOINT_ENABLED=true`, `OBSTACLE_GUARD_MODE=on`, `NAV_KEEP_GAIT_ON_ARRIVAL=true`(운영 PC 컨테이너의 실제 값은 `docker exec control-backend printenv <키>` 로 확인).
- 의도적으로 compose 목록이 다른 키: `ARM_MOCK`(local 에서 일부러 뺌), `SEED_*_PASSWORD`(운영 local 에는 없음, 신규 PC 용).
- **새 환경 변수를 추가할 때 함께 고칠 곳 4곳**: ① `Backend/app/robot_io/config.py`(`_env_str/_env_int/_env_bool`, 기본값은 "꺼짐·지금 동작 유지") ② compose 3개(`local`·`windows`·`linux`)의 backend `environment:` 에 `- 키=${키:-기본값}` 와 설명 주석 ③ `.env.example` ④ 필요하면 `.env`(바꾸기 전 `.env.bak_날짜_주제` 백업).
- **대조 방법:** `.env` 의 키 중 compose 에서 `${키…}` 로 쓰이지 않는 것을 찾습니다(값은 출력하지 않음). compose 파일마다 이름을 바꿔 세 번 실행합니다.
  ```bash
  for k in $(grep -E '^[A-Z_0-9]+=' .env | cut -d= -f1); do
    grep -qE '\$\{'"$k"'[:}]' docker-compose.local.yml || echo "compose 에 없음: $k"
  done
  ```
  `COMPOSE_FILE` 처럼 compose 안에서 쓰지 않는 키는 정상적으로 나옵니다. 그 밖의 키가 나오면 backend `environment:` 에 추가합니다.
- 값만 바뀌면 재빌드 없이 `up -d --no-deps --force-recreate backend`. 적용 후 `docker exec control-backend printenv <키>`(비밀값 키는 하지 않음).
- `.env.bak_*`, `Backend/data/_*.py`, `robot_vision/thermal.env` 에는 **비밀값이 들어 있으니 커밋·공유에서 제외**합니다(`.gitignore` 로 제외됨).
- **열화상 카메라 계정**은 `.env` 가 아니라 `robot_vision/thermal.env` 에 둡니다. `robot_vision/thermal_env.sample` 을 `thermal.env` 로 복사해 `THERMAL_CAMERA_PASS` 를 채우거나(`THERMAL_CAMERA_IP/PORT/USER` 는 기본값 있음) 같은 이름의 환경 변수로 줍니다. 스크립트(`thermal_max_overlay.py`)가 도는 장비에 이 파일이 있어야 하며, 값이 없으면 종료합니다.

## 3. 장비별 배포 절차

> 배포는 되돌리기 어렵고 운영 중인 로봇에 영향을 줍니다. 모든 장비에서 **① 사전 점검 → ② 승인 → ③ 실행 → ④ 사후 확인 → ⑤ 되돌리기 준비** 순서를 지키고, **한 번에 한 사람(한 곳)만** 배포합니다(여러 명이 동시에 배포해 서비스가 5분 중단된 적이 있음). 코드 변경은 먼저 사전 시뮬레이션(`09_개발_검증_방법.md`)을 거칩니다.
>
> 아래 명령은 모두 **일반 셸 명령과 저장소 안의 도구**만 씁니다. 별도 자동화 도구 없이 따라 할 수 있습니다. 명령 안의 compose 파일 이름·프로젝트명은 그 PC 에서 실제로 쓰는 것으로 바꿉니다(1절).
> Windows Git Bash 에서 컨테이너 안 경로를 인자로 줄 때는 명령 앞에 `MSYS_NO_PATHCONV=1` 을 붙입니다.

### 3-1. 관제 (관제 PC 의 도커: backend·frontend)

**① 사전 점검 (읽기 전용)**
1. 컨테이너 상태: `docker compose -f <compose 파일> -p <프로젝트명> ps` — backend·db 가 `Up` 이어야 합니다.
2. **진행 중인 안내 세션·작업 회차가 0건인지** 확인합니다(배포 중 컨테이너가 재생성되면 진행 중인 안내가 끊깁니다). DB 컨테이너에 접속해(`docker exec -it control-db mariadb -uroot -p <스키마>`, 비밀번호는 프롬프트에 입력) 조회합니다.
   ```sql
   SELECT COUNT(*) FROM service_session WHERE EndedAt IS NULL;   -- 안내 세션
   SELECT COUNT(*) FROM schedule_run WHERE Result = 'running';   -- 작업 회차
   ```
3. **이번에 나갈 변경 확인:** 이미지는 작업 폴더 **전체**로 만들어지므로 다른 사람이 고치던 미완성 변경도 같이 나갑니다. `git status`·`git diff --stat` 로 변경 목록을 보고, 이번 배포와 무관한 변경이 있으면 정리하거나 확인을 받습니다. 백엔드 변경이 없으면 `frontend` 만, 화면 변경이 없으면 `backend` 만 배포합니다.
4. **환경 변수 전달 확인:** `.env` 의 키가 compose 의 `environment:` 목록에 있는지 봅니다(2절의 대조 방법).

**② 승인:** 진행 중 작업 수, 같이 나갈 변경 목록, 실행할 명령을 정리해 책임자에게 확인받습니다.

**③ 실행**
1. **되돌릴 수 있게 이미지에 이름표를 붙입니다.**
   ```bash
   docker tag und-control-backend:latest  und-control-backend:bak_<날짜>
   docker tag und-control-frontend:latest und-control-frontend:bak_<날짜>
   ```
   (이미지 이름은 `docker images` 로 확인합니다.)
2. 다시 빌드해 올립니다. 빌드는 수 분 걸리고(메모리가 모자라면 10분 넘은 적 있음) 바뀐 쪽만 지정합니다.
   ```bash
   docker compose -f <compose 파일> -p <프로젝트명> up -d --build --no-deps backend frontend
   ```
3. 환경 변수만 바뀌었으면 빌드 없이 `up -d --no-deps --force-recreate backend` 로 충분합니다.
- **금지:** `docker compose down -v`(DB 볼륨 삭제). 운영 DB 는 조회만 하고, 검증은 격리 DB·`sim/` 에서 합니다.

**④ 사후 확인**
```bash
docker compose -f <compose 파일> -p <프로젝트명> ps                       # backend 가 healthy
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8010/api            # 200
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8010/robot/status   # 로그인 없이 401 이 정상
curl -s -o /dev/null -w "%{http_code}\n" http://localhost:3001/               # 200
docker logs --since 10m control-backend                                       # 기동 오류 없는지
```
- 화면을 바꿨다면 바뀐 문구가 번들에 들어갔는지 `docker exec control-frontend grep -rl "<바뀐 문구>" /usr/share/nginx/html | head -3` 로 확인합니다.
- 환경 변수를 바꿨다면 `docker exec control-backend printenv <키>` 로 값이 들어갔는지 봅니다(비밀값 키 제외).

**⑤ 되돌리기:** 이름표를 `latest` 로 되돌린 뒤 **`--build` 없이** 다시 띄웁니다.
```bash
docker tag und-control-backend:bak_<날짜>  und-control-backend:latest
docker tag und-control-frontend:bak_<날짜> und-control-frontend:latest
docker compose -f <compose 파일> -p <프로젝트명> up -d --no-deps backend frontend
```
- 배포 기록에 대상·시각·이름표·확인 결과·되돌리기 명령·**커밋 여부**·실기 확인이 필요한 항목을 남깁니다.

### 3-2. NOS 중계기 (NOS 보드의 `receiver.py` 등)

중계기는 NOS 의 `/home/user/Control_system/receiver.py` 로 돕니다. NOS 서비스 이름은 보드마다 다릅니다: 296호기 `receiver`·`relay_charge`·`relay_motion`, 669호기 `control-receiver`·`relay-charge`·`relay-motion`(배포 도구가 접속 뒤 실제 이름을 골라 씀). `relay_map.py` 도 함께 올리지만 서비스가 아니라서 재시작 대상이 아닙니다.

배포 도구는 저장소의 `robot_receiver/tools/nos_receiver.py` 이며, **관제 backend 컨테이너 안에서** 실행합니다(`.env` 의 `NOS_HOST/PORT/USER/PASSWORD` 사용, 비밀번호는 출력하지 않음). 관제 PC 가 로봇 망(층 Wi-Fi + 10.21.31.0/24 경로)에 있어야 하며, 접속 시간이 초과되면 망부터 확인합니다.

**① 사전 점검**
1. 진행 중인 안내 세션·작업 회차가 0건인지 확인합니다(3-1 의 조회). 서비스 3개가 수 초 끊기므로 **걷는 중이면 멈출 수 있습니다.**
2. 로컬 문법 검사: `python -m py_compile robot_receiver/receiver.py`
3. 도구와 올릴 파일을 컨테이너 `/tmp` 로 복사합니다. **컨테이너를 다시 만들면 `/tmp` 가 비워지므로 매번 복사부터 합니다.**
   ```bash
   docker cp robot_receiver/tools/nos_receiver.py control-backend:/tmp/nos_receiver.py
   docker cp robot_receiver/receiver.py           control-backend:/tmp/receiver_new.py
   docker cp robot_receiver/relay_map.py          control-backend:/tmp/relay_map_new.py   # 있으면
   ```
4. **차이 확인(읽기 전용):** `docker exec control-backend python /tmp/nos_receiver.py check` — 로컬과 NOS 본의 diff 를 봅니다. **일부러 다르게 둔 부분이 있었으므로**(10-20: 다지점 기능만 얹고 위치 age 기능은 뺌) diff 전체를 읽고, 이번 변경과 무관한 차이가 같이 올라가도 되는지 확인합니다.

**② 승인:** 로컬·NOS 해시, 바뀌는 줄 요약(이번 변경 / 그 밖), 재시작 영향을 정리해 확인받습니다.

**③ 실행:** `docker exec control-backend python /tmp/nos_receiver.py deploy`
- 도구가 하는 일: NOS 에 `receiver.py.bak-<날짜-시각>` 백업 → 교체 → **NOS 에서 문법 검사(NOS 파이썬은 3.8, 실패하면 백업으로 자동 복구하고 재시작하지 않음)** → 서비스 3개를 **함께** 재시작. receiver 만 재시작하면 충전 상태가 "대기"로 보이는 문제가 있어(10-11) 셋을 함께 올립니다.

**④ 사후 확인:** `docker exec control-backend python /tmp/nos_receiver.py status` — 세 서비스 `active`, receiver 최근 로그에 오류 없음. 관제 화면의 로봇 상태·충전 표시가 정상인지 `docker logs --since 2m control-backend` 와 함께 봅니다. 속도 매핑을 바꿨다면 `... nos_receiver.py speed`(읽기 전용)로 확인합니다.

**⑤ 되돌리기(NOS 에서, sudo 필요):**
```bash
cd /home/user/Control_system && cp -p receiver.py.bak-<날짜-시각> receiver.py \
  && sudo systemctl restart receiver relay_charge relay_motion
# 669호기: sudo systemctl restart control-receiver relay-charge relay-motion  (relay_map.py 도 같은 꼬리표 백업으로 되돌림)
```

**장애물 감지 노드(`obstacle_guard.py`·`obstacle_core.py`, 서비스 `obstacle-guard`)** — 중계기 서비스 3개를 **재시작하지 않는** 별도 배포입니다.
```bash
docker cp robot_receiver/obstacle_core.py     control-backend:/tmp/obstacle_core_new.py
docker cp robot_receiver/obstacle_guard.py    control-backend:/tmp/obstacle_guard_new.py
docker cp robot_receiver/obstacle_ignore.json control-backend:/tmp/obstacle_ignore_new.json
docker exec control-backend python /tmp/nos_receiver.py guard-check     # 읽기 전용: 로컬 대 NOS 차이, 서비스·설정 유무
docker exec control-backend python /tmp/nos_receiver.py guard-status    # 읽기 전용: 상태·로그·기록 크기
docker exec control-backend python /tmp/nos_receiver.py guard-deploy    # 백업·교체·NOS 문법 검사(실패면 되돌림), 서비스가 있으면 그것만 재시작
docker exec control-backend python /tmp/nos_receiver.py guard-install   # 서비스·설정 파일 생성(설정은 없을 때만, 기본 '기록만')
docker exec control-backend python /tmp/nos_receiver.py guard-remove    # 서비스를 끄고 지움(파일·설정·기록은 남김)
docker exec control-backend python /tmp/nos_receiver.py guard-live      # 설정 OBSTACLE_RECORD_ONLY=0(실제 정지)으로 바꾸고 감지 노드만 재시작
docker exec control-backend python /tmp/nos_receiver.py guard-record    # OBSTACLE_RECORD_ONLY=1(기록만)로 되돌림
```
- 관제가 장애물 감지를 켜는 것은 **안내 시나리오 이동 중**일 때만이고(`OBSTACLE_GUARD_MODE`: off/record/on), NOS 설정 `OBSTACLE_RECORD_ONLY=1`(설치 기본)이면 관제가 `on` 이어도 이동을 취소하지 않습니다(실기 확인 전 안전장치).
- 기록 `/home/user/Control_system/obstacle_rec/rec_*.jsonl`(상한 300MB), 서비스는 `Nice=10`·`CPUQuota=60%`.

**NOS 에서 알아 둘 것**
- 토픽을 볼 때는 **`ros2 topic list --no-daemon`**(그냥 돌리면 `_ros2_daemon` 이 코어 하나를 100% 사용합니다). NOS 는 8코어 중 4~7 이 제조사 전용이고, 부하 평균이 높아도 CPU 포화와 같지 않습니다.
- NOS 시계는 관제보다 수십 초 빠르므로 기록에는 한국 시각(관제 기준)을 씁니다.

### 3-3. Jetson 음성 (`robot-voice`)

- 실행본은 **`/opt/robot/voice/robot_voice`** 입니다. 작업 폴더(`/home/und02/project/robot_voice`)만 바꾸면 **적용되지 않습니다**(10-12). 반대로 작업 폴더가 설치본보다 오래된 적도 있어(10-09·10-21) 반드시 세 곳(내 PC·Jetson 작업 폴더·설치본)을 대조한 뒤 **바뀐 파일만** 올립니다.
- Jetson 주소는 층 Wi-Fi 기준 `172.30.1.44`(키 인증 ssh)입니다. 다른 망이면 그 망의 주소로 접속합니다. 아래에서 `<jetson>` 은 접속 대상입니다.
- `install.sh` 는 배포에 쓰지 않습니다(폴더 전체를 덮고 파이썬 패키지까지 올려 시연 직전에는 위험하고 설정 일부를 다시 묻습니다). 새 패키지가 필요할 때만 따로 정합니다.

**① 사전 점검**
1. 진행 중인 안내 세션이 없는지 확인합니다(3-1 의 조회). 재시작하는 동안 음성 응대가 중단됩니다.
2. 올릴 파일의 로컬 문법 검사: `python -m py_compile robot_voice/<파일>.py`
3. **세 곳 해시 대조**
   ```bash
   sha256sum robot_voice/<파일>                                                   # 내 PC
   ssh <jetson> "sha256sum /home/und02/project/robot_voice/<파일> /opt/robot/voice/robot_voice/<파일>"
   ```
   - 내 PC 만 다르면 배포 후보입니다.
   - **설치본이 내 PC·작업 폴더 둘 다와 다르면** 설치본에만 있는 수정이 있다는 뜻입니다. `diff` 로 줄 차이를 보고 덮어써도 되는지 확인합니다(필요하면 "설치본 + 이번 변경분"을 합친 파일을 만들어 올립니다).

**② 승인:** 올릴 파일 목록(이번 변경 / 그 밖), 설치본과의 차이, 재시작 영향을 정리해 확인받습니다.

**③ 실행**
1. 작업 폴더에 올립니다(기존 파일은 백업).
   ```bash
   ssh <jetson> "cp -p /home/und02/project/robot_voice/<파일> /home/und02/project/robot_voice/<파일>.bak_<날짜>"
   scp robot_voice/<파일> <jetson>:/home/und02/project/robot_voice/
   ```
2. 설치본을 교체하고 **30초 뒤 재시작을 예약**합니다(sudo 비밀번호 필요). 소유자·권한이 기존 설치본과 같아야 하므로 `ls -l` 로 확인합니다.
   ```bash
   sudo cp -p /opt/robot/voice/robot_voice/<파일> /opt/robot/voice/robot_voice/<파일>.bak_<날짜>
   sudo cp    /home/und02/project/robot_voice/<파일> /opt/robot/voice/robot_voice/<파일>
   sudo systemd-run --on-active=30 --unit=robot-voice-delayed-restart systemctl restart robot-voice
   ```
   - **재시작을 ssh 세션 안에서 바로 하지 않습니다.** `und02` 는 Linger 가 꺼져 있어 ssh 로그인마다 pulseaudio 가 새로 떠 USB 스피커(UACDemo)를 잠깐 잡고, 그 순간 시작한 robot-voice 는 장치 목록에서 스피커를 빠뜨려 "output 장치를 찾지 못했다 → aborted_tts"가 납니다(10-27 두 번 재현).
   - 명령을 실행한 뒤 **1분 동안 Jetson 에 ssh 접속하지 않습니다.**

**④ 사후 확인(1분 뒤)**
```bash
ssh <jetson> "systemctl is-active robot-voice; journalctl -u robot-voice -n 50 --no-pager"
```
- `active`, 로그에 Traceback 없음, 세 곳 해시가 모두 같은지 다시 대조합니다.
- 안내 시작을 눌러 첫 멘트가 나오는지(실기) 확인합니다. 로그에 `output 장치를 찾지 못했다` 가 있으면 위 예약 재시작을 다시 합니다.
- 새 설정 키를 쓰는 변경이면 실행 중 설정(`/etc/robot-voice.env`)에 키가 있는지 봅니다(없으면 sudo 로 추가).

**⑤ 되돌리기:** 설치본의 `.bak_<날짜>` 를 원래 이름으로 복사하고 다시 30초 뒤 재시작을 예약합니다.
```bash
sudo cp -p /opt/robot/voice/robot_voice/<파일>.bak_<날짜> /opt/robot/voice/robot_voice/<파일>
sudo systemd-run --on-active=30 --unit=robot-voice-delayed-restart systemctl restart robot-voice
```

**Jetson 에서 알아 둘 것**
- **관제 화면의 "음성 튜닝값"(`sttModel` 등)은 Jetson 이 사용하지 않습니다.** 이 설정은 `/etc/robot-voice.env` 로 합니다(시나리오·목적지 사전은 번들로 반영).
- 마이크가 먹통이면(USB `-71`): 재장착 없이 `authorized` 토글 → 포트 리셋 → 재토글 → robot-voice 재시작(10-11 복구 절차).

### 3-4. 반영 순서와 짝 규칙
- 관제 설정(`NAV_KEEP_GAIT_ON_ARRIVAL`·`NAV_CONTINUOUS_PASS` 등)과 중계기 환경 변수(`NAV_CONTINUE_SKIP_RESET`)는 **짝**이라 한쪽만 켜면 오히려 나빠집니다.
- 장비를 건드리는 변경(NOS·Jetson)은 걷는 중·응대 중이 아닐 때만 하고, **시연 직전에는 하지 않습니다.**
- 배포 뒤 "실기 미확인" 항목은 `12_남은일_결정대기_위험.md` 3절 표에 올려 실기 일정 때 확인합니다.

## 4. 새 PC·새 로봇 설치 체크리스트 (코드 기준)

1. `.env.example` → `.env` 복사, `JWT_SECRET_KEY` 등 채움(`COMPOSE_FILE` 지정).
2. 로봇 망: `ROBOT_IP`·`RECEIVER_IP`·`NOS_HOST` 확인, 관제 PC에서 10.21.31.0/24 경로 추가(Jetson 경유), `MediaMTX/mediamtx.local.yml` 영상 원본 주소.
3. DB: 신규는 `db/init` 덤프 자동 import(윈도우 compose), 기존은 `DATABASE_URL`.
4. NOS: 중계기·릴레이·`obstacle-guard`·`robot-network-watchdog` 설치, 맵(`UND_*`) 업로드(**맵 번호가 새로 생기므로 설정의 맵 번호 확인**).
5. Jetson: `install.sh`(최초 1회만) → `/etc/robot-voice.env` 필수 4개(`OPENAI_API_KEY`·`AGENT_TOKEN`·`ROBOT_ID`·`BACKEND_BASE`) → stt-server·respeaker-tune 유닛.
6. 다른 로봇(예: 669)을 296 자리에 붙일 때: NOS 에 맵·중계기가 있는지, 서비스 이름(하이픈 유무)이 다른지, 관제 `robot_info` 의 번호와 Jetson `ROBOT_ID` 를 확인(10-29 사례 — 669 는 맵 0개·옛 중계기였음).
7. 다른 망으로 옮길 때: Jetson·관제 PC 주소와 `BACKEND_BASE`·`mediamtx.local.yml` 호스트를 함께 바꿈(`02_네트워크_포트_장비.md` 4절).
