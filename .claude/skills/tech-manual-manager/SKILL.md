# 기술 업무 매뉴얼 자동 관리 (tech-manual-manager)

세션에서 한 작업 중 **다음에 같은 일을 다시 할 때 필요한 기술 정보**만 골라 매뉴얼 저장소에 반영한다.
프로젝트 `docs/` 는 참조 자료일 뿐 저장 위치가 아니다.

- 인자 `$ARGUMENTS` 에 `--dry-run` 이 있으면 1~6단계(분석·분류·반영 계획)까지만 하고 **파일을 하나도 쓰지 않는다.**
- 그 밖의 인자는 추가 지시(대상 작업 한정 등)로 따른다.

도구: `python .claude/skills/tech-manual-manager/scripts/manual_tool.py <명령>` (아래 `TOOL`). 결과는 JSON.

| 명령 | 하는 일 |
|---|---|
| `resolve` | MANUAL_ROOT 확인(필수 파일·분류 폴더·쓰기 가능) |
| `set-root <경로>` | 확인된 경로를 `config.local.json` 에 저장(실제 저장소가 아니면 저장 거부) |
| `inventory` | 저장소 전체 매뉴얼 목록(경로·제목·상태·검증일), 루트 미분류 문서 포함 |
| `search <단어...>` | 제목·본문 검색, 많이 맞는 순 + 적용 범위 |
| `check <파일...>` | `_TEMPLATE.md` 를 그때그때 읽어 머리표·장 제목·순서·상태값·비밀값 검사 |
| `init-log` | `MANUAL_LOG.md` 가 없을 때만 머리말로 생성(있으면 보존) |
| `source-info` | 프로젝트 저장소 이름·URL(사용자 정보 제거)·브랜치·HEAD 커밋 |

## 지켜야 할 것 (모든 단계 공통)

1. 사용자가 이 skill 을 부른 때에만 매뉴얼을 쓴다. 일반 개발 대화 중에는 쓰지 않는다.
2. 매뉴얼 저장소 위치를 추정해 새 폴더를 만들지 않는다. 분류 폴더가 없으면 만들지 말고 보고한다.
3. 기존 문서를 이동·삭제·병합·대규모 축약하지 않는다(필요하면 "검토 필요"로 보고).
4. 양식 복사본을 따로 두지 않는다. 쓸 때마다 `MANUAL_ROOT/_TEMPLATE.md` 를 직접 읽는다. 양식 자체는 고치지 않는다.
5. 근거 없는 내용은 쓰지 않고 `확인 필요` 로 적는다. 관찰 사실(`확인`)·원인 가설(`추정`)·실행 전 조치(`미검증`)를 나눈다.
6. 문서화를 위해 로봇을 움직이거나 공유기·Jetson·NOS·운영 DB·컨테이너 설정을 바꾸지 않는다. 운영 상태는 조회만.
7. 비밀값(API Key·비밀번호·토큰·인증 파일 내용, `.env`·`.env.bak_*`·`Backend/data/_*.py`·`MediaMTX/mediamtx.yml` 의 값)을 매뉴얼·보고에 옮기지 않는다. 변수 **이름**만 적는다.
8. Git commit·push 하지 않는다(매뉴얼 저장소·프로젝트 모두).
9. 문장은 국문으로. 영문은 명령·파일명·변수명 등 꼭 필요한 것만.

## 1단계. MANUAL_ROOT 확인

1. `TOOL resolve` 실행. 환경 변수 `M20_MANUAL_ROOT` 가 설정 파일보다 우선한다.
2. `ok: true` 이면 그 경로를 MANUAL_ROOT 로 쓴다. 이후 모든 매뉴얼 경로는 이 기준.
3. `미설정`·폴더 없음이면: `README.md`·`_TEMPLATE.md` 를 함께 가진 `M20_TECH_MANUAL` 폴더를 찾아(예: `Glob` 로 `C:/Workspace/**/M20_TECH_MANUAL/_TEMPLATE.md`) 후보를 **사용자에게 보여 주고 확인을 받은 뒤** `TOOL set-root <경로>` 로 저장한다. 찾지 못하면 멈추고 경로를 묻는다. `docs/` 로 대신하지 않는다.
4. `writable: false` 이거나 쓰기 도구가 권한 거부되면, 무엇이 막혔는지 알리고 `.claude/settings.local.json` 의 `permissions.additionalDirectories` 에 MANUAL_ROOT 추가를 안내한다.
5. `problems` 의 분류 폴더 누락은 해당 폴더로 가야 할 문서만 "검토 필요"로 돌린다.

## 2단계. 저장소 규칙 읽기

- `MANUAL_ROOT/_TEMPLATE.md`, `MANUAL_ROOT/README.md` 를 **Read 로 직접** 읽는다(머리표 항목, 검증 상태 정의, 원본 참조 표, 변경 이력 표, 목차 표 형식).
- `MANUAL_ROOT/MANUAL_LOG.md` 가 있으면 최근 기록을 읽어 같은 작업이 이미 반영됐는지 본다.
- 이름이 `(예시)` 로 시작하는 파일은 작성 참고용 예시다. 문체·상세도 참고로만 읽고, 매뉴얼로 갱신·중복 판정·목차 등록하지 않는다(`inventory`·`search` 에서도 빠진다).
- README 의 문서 구조 설명이 실제 폴더(`01_Setup` ~ `06_Test_Validation`)와 다르면 README 구조 절은 고치지 않고 "검토 필요"로 보고한다(구조 변경은 사용자 결정).

## 3단계. 세션 작업 자료 모으기

세션 기록을 전부 볼 수 있다고 가정하지 않는다. 확인한 자료만 근거로 쓴다.

| 우선 | 자료 | 쓰는 법 |
|---|---|---|
| 1 | 지금 대화에서 한 작업(요청·결정·실행 명령·출력·검증 결과) | 1차 근거. 실행 출력이 있어야 "실행했다"고 적는다 |
| 2 | `git status --short`, `git diff --stat`, `git diff <대화에 나온 파일>`, `git log --oneline -15` | 대화에 나온 변경의 실제 내용 확인 |
| 3 | 바뀐 소스·설정 파일 | 명령·설정값·흐름 확인(비밀값 제외) |
| 4 | 이번 세션에서 쓴 `docs/<종류>/<오늘 날짜>/…` 보고서, `sim/` 시나리오·결과 | 검증 근거 |
| 5 | 사용자가 준 로그·화면·측정값 | 현장 조작·네트워크 설정처럼 Git 에 안 남는 작업의 유일한 근거 |
| 6 | 기존 매뉴얼(`TOOL inventory`) | 중복·충돌 확인 |

- 작업 폴더에는 **다른 세션의 미커밋 변경이 많다.** 대화에 나오지 않은 변경은 이번 세션 작업으로 보지 않는다. 필요하면 "세션 밖 변경(대상 아님)"으로 개수만 보고한다.
- 배포 여부·설정값처럼 상태를 적어야 하면 메모가 아니라 대화 안의 실제 확인 출력(실행 중 환경 변수·컨테이너 코드·설치본 해시)을 근거로 한다. 없으면 `확인 필요`.

## 4단계. 작업 단위로 나누고 A/B/C 분류

세션 작업을 "다시 수행할 수 있는 업무 하나" 단위로 나눈 뒤 각각을 분류한다.

| 분류 | 기준 | 처리 |
|---|---|---|
| **A. 자동 반영** | 새 기능의 설정·실행 절차 / 기존 기능의 사용·운영 방법 변경 / 반복·중요 장애의 해결 절차 / 로봇 제어 방식·인터페이스 변경 / API·시스템 간 데이터 흐름 변경 / 재사용 가능한 성능 개선 / 시험·검증 절차의 실질 변경 / 재수행에 필요한 기술 정보(환경 변수·명령·판정 기준) | 반영 |
| **B. 검토 필요** | 기존 매뉴얼과 내용 충돌 / 검증 안 된 해결책을 "해결 절차"로 써야 하는 경우 / 구현 상태 불확실 / 신규·갱신 판단 곤란 / 실제 동작 확인 불가 / 기존 내용 삭제·대규모 축약·이동·병합 필요 / 저장소 구조 변경 필요 | 반영하지 않고 보고 |
| **C. 자동 제외** | 색상·간격 등 스타일 / 오탈자 / 동작 무관 이름 변경 / 실행·설정 방식이 그대로인 리팩터링 / 재사용 가치 없는 일회성 디버깅 / 매뉴얼과 무관한 임시 작업 | 제외 사유만 보고 |

- 단순 UI 변경이라도 운영자 조작 순서·버튼 위치·판정 화면이 바뀌면 A 로 다시 본다.
- 계획·제안·승인 대기 상태(미구현)는 README 규칙상 매뉴얼 대상이 아니다. 이미 있는 매뉴얼의 "주의"에 한 줄로 알릴 가치가 있을 때만 A, 아니면 C(사유: 미구현).
- 구현은 됐지만 실기 미확인이면 A 로 반영하되 상태를 낮게 적는다(7단계 표). "해결됐다"고 단정해야만 의미가 있는 내용이면 B.

## 5단계. 기존 매뉴얼 검색 → 신규/갱신 판단

A 로 분류한 작업마다:

1. `TOOL search <핵심어 2~4개>` (국문 기능명 + 파일명·변수명·API 경로 등). 루트에 있는 미분류 문서도 검색 대상이다.
2. 상위 후보 문서를 Read 해 **제목·1장 적용 범위·3장 절차**를 비교한다. 파일명만 보고 정하지 않는다.
3. 판단:
   - 같은 업무 절차를 다루는 문서가 있으면 → **그 문서를 갱신**(있는 자리에서. 루트 미분류 문서도 옮기지 않는다).
   - 독립된 절차가 필요하면 → **신규**.
   - 복잡하거나 반복되는 장애 → `05_Troubleshooting` 독립 문서(기능 문서에는 링크와 한 줄 요약만).
   - 독립된 시험 절차·측정 결과 → `06_Test_Validation`.
4. 한 작업이 여러 문서에 걸려도 **같은 내용을 두 곳에 쓰지 않는다.** 역할을 나눈다:
   - 기능 문서: 정상 구성·설정·실행 방법
   - 장애 문서: 증상·재현·원인(확인/추정)·복구
   - 검증 문서: 시험 환경·절차·측정값·판정 기준
   나머지 문서에는 상대 경로 링크로 연결한다.

## 6단계. 분류 폴더와 파일 이름

문서는 대표 분류 하나에만 둔다. 주된 실행 목적으로 정한다.

| 폴더 | 대상 |
|---|---|
| `01_Setup` | Wi-Fi·DHCP·Jetson·장비 연결·개발 환경 |
| `02_Robot_Control` | 지도 작성·측위·주행·장소(POI)·노드망·로봇 동작·상태·안전 제어 |
| `03_Control_Platform` | 대시보드·관제 화면·API·로봇 관리·관제 기반 통합 제어 |
| `04_Service_Functions` | 음성 인식·합성(STT/TTS)·Whisper·음성 대화·비전·OCR·사람 추적 |
| `05_Troubleshooting` | 반복 장애·원인 분석·복구 절차 |
| `06_Test_Validation` | 기능 검증·성능 시험·통합 시험·검증 결과 |
| `07_Build_Deploy` | Frontend·Backend 빌드, Docker 이미지·컨테이너 배포, Jetson·관제 PC 배포, 서비스 실행·중지·재시작, 자동 실행, 롤백, 릴리스 관리 |

예: 관제 버튼 → 로봇 이동 전체 흐름 = `03`, M20 이동 명령 처리 방식 = `02`, Jetson Whisper 실행 설정 = `04`, 음성 무음 오인식 반복 장애 = `05`. 

예: Docker 이미지 빌드 및 관제 서버 배포 = `07`, 배포 중 반복적으로 발생하는 오류의 원인 분석·복구 = `05`, 배포 후 별도 통합 검증 절차 = `06`.

- 파일 이름은 기존 관례대로 `영문_단어_연결.md`(예: `Relocalization_Procedure.md`). 같은 이름이 있으면 새로 만들지 말고 5단계로 돌아간다.
- 제목(`# `)은 양식의 "작업 대상 + 수행 목적"을 국문으로.

`--dry-run` 이면 여기서 멈추고 13단계 형식으로 **반영 계획**(문서별 신규/갱신·경로·넣을 내용 요약)만 보고한다.

## 7단계. 작성 규칙 (신규·갱신 공통)

- 신규: `_TEMPLATE.md` 를 방금 읽은 그대로의 머리표·장(1~8)·표 머리줄로 쓴다. 장 아래 소항목은 필요한 만큼 추가할 수 있지만 장을 빼거나 순서를 바꾸지 않는다. 쓸 내용이 없는 칸은 `해당 없음` 또는 `확인 필요`.
- 양식의 안내문(`[예: …]`, `YYYY-MM-DD`, 설명용 인용 줄)은 실제 값으로 바꾸거나 지운다. `TOOL check` 의 `template_placeholders_left` 가 0 이어야 한다(일부러 남긴 `확인 필요` 는 별개).
- 명령은 **세션에서 실제 실행했거나 저장소 skill·스크립트에 정해진 것**만 적고 실행 위치(관제 노트북 / NOS / Jetson / 컨테이너)를 붙인다. sudo 가 필요한 명령은 "사용자가 직접 실행"으로 표시한다.
- 날짜는 절대 날짜(YYYY-MM-DD). 시각이 중요하면 기준 시계를 적는다(백엔드 도커 로그는 세계 표준시, 본체·NOS 시계는 관제보다 수십 초 빠름).
- 빌드·배포 관련 매뉴얼은 `07_Build_Deploy`로 분류하고, 실제 사용한 실행 명령어와 실행 환경을 명시한다.
- 빌드 및 배포에 사용한 주요 버전 정보(Docker 이미지 태그, Git 커밋 ID, 런타임 버전 등)는 확인 가능한 범위에서 기록한다.
- 배포 매뉴얼에는 사전 준비사항, 빌드, 배포, 서비스 실행, 정상 동작 확인 및 롤백 절차를 필요한 범위에서 작성한다.
- 배포 과정에서 발생한 일회성 오류는 기존 매뉴얼의 오류 대응 항목에 기록할 수 있으며, 반복되거나 복잡한 장애는 `05_Troubleshooting`에 별도로 작성한다.
- 배포 이후 독립적인 성능 시험이나 통합 검증이 필요한 경우 `06_Test_Validation` 문서와 연결한다.
- 문서화를 위해 실제 배포, 서비스 재시작 또는 롤백을 임의로 실행하지 않는다.

### 검증 상태 정하기

상태 이름과 의미는 `_TEMPLATE.md`·`README.md` 정의를 따른다. 아래는 판정 기준이다.

| 근거 | 문서 상태 | 최종 검증일 | 4장 결과 칸 |
|---|---|---|---|
| 코드·설정만 있음, 실행 안 함 | 초안 | 미검증 | 미검증 |
| 세션에서 시뮬(`sim`)·단위 시험·빌드·API 응답을 실제 실행해 통과, 현장 장비 대상 절차 | 검증 중 | 미검증(현장) — 시험 통과일은 4장 "검증 수행일·환경"에 시뮬/시험으로 명시 | 시험명: 통과 / 현장: 미검증 |
| 개발 PC 에서 끝나는 절차를 세션에서 처음부터 끝까지 실행해 완료 기준 확인 | 검증 완료 | 그 실행 날짜 | 통과 |
| 사용자가 제공한 현장 실기 결과(로그·측정값·화면)로 완료 기준 확인 | 검증 완료 | 실기 날짜 | 통과(증빙 경로) |
| 이미 검증 완료였던 문서의 절차·환경이 이번에 바뀌었고 재검증 없음 | 개정 필요 | **기존 값 유지** | 바뀐 항목만 미검증 |
| 배포 안 됨·커밋 안 됨 | 상태와 별개로 머리표 "적용 SW/펌웨어 버전"에 `미배포`·`미커밋` 명시 | — | — |

- 코드가 있다는 사실만으로 동작한다고 쓰지 않는다. 시험을 실행하지 않았으면 "시험 완료"라고 쓰지 않는다.
- 기존 문서의 검증 완료를 바뀐 환경에 그대로 이어 쓰지 않는다. 최종 검증일은 실제 검증 근거가 있을 때만 바꾼다.

### 원본 참조(7장)

- `TOOL source-info` 결과로 원본 저장소 이름·URL·브랜치·커밋을 적는다. 매뉴얼 저장소는 프로젝트와 별개라 상대 경로로 이어지지 않으므로, 파일은 **"저장소 기준 상대 경로 + 커밋 ID"** 로 적는다(예: `Backend/app/navigation/send_move.py` @ `9843098`).
- 작업 폴더에만 있고 커밋 안 된 변경이면 `HEAD <커밋> 이후 미커밋` 으로 적는다.
- 소스·설정·로그·스크립트를 매뉴얼 저장소에 복사하지 않는다. 짧은 설정값·명령만 본문에 적는다.
- 관련 매뉴얼끼리는 문서 위치 기준 상대 경로로 링크한다(예: `03_Control_Platform/` 문서에서 루트 문서는 `../Relocalization_Procedure.md`).
- 이미지는 `MANUAL_ROOT/assets/<주제>/` 에 둘 때만 링크한다. 이번 세션에 실제 파일이 없으면 넣지 않는다.

## 8단계. 기존 문서 갱신 규칙

- 바뀐 절차·값만 고친다. 근거 없이 문단을 지우거나 크게 줄이지 않는다(그래야 하면 B).
- 기존 내용과 이번 근거가 충돌하면: 이번 근거가 세션의 실제 실행 출력이면 고치고 8장에 "정정: <이전> → <현재>, 근거 <…>"를 남긴다. 근거가 약하면 고치지 말고 B.
- 머리표 "최종 수정일"을 오늘로, 8장 변경 이력 표에 한 줄 추가(날짜·변경 내용 및 사유·변경 후 검증 상태·비고). 이전 이력 줄은 고치지 않는다.
- 문서의 줄바꿈 방식(LF/CRLF)과 인코딩(UTF-8)은 원본대로 둔다.

## 9단계. 양식 검사

반영한 파일마다 `TOOL check <MANUAL_ROOT 기준 경로>` 실행. `ok: false` 면 고친 뒤 다시 검사한다. 끝까지 못 고치면 보고에 남긴다.

## 10단계. README 목차 갱신

- 신규 문서: README "매뉴얼 목차" 표 형식(`| 영역 | 문서 | 상태 | 비고 |`) 그대로 한 줄 추가. 링크는 README 기준 상대 경로, 상태는 문서 머리표와 같게.
- 기존 문서의 상태가 바뀌었고 목차에 그 문서 줄이 있으면 상태 칸만 고친다. 목차에 없던 기존 문서는 이번에 갱신한 것만 추가한다(일괄 등록 금지).
- 목차 외 절(목적·구조·규칙)은 고치지 않는다.

## 11단계. MANUAL_LOG 기록

1. 없으면 `TOOL init-log` (README 규칙과 충돌 없음 확인 후).
2. 실제로 파일에 반영한 문서만 한 줄씩 끝에 추가:
   `| YYYY-MM-DD | <MANUAL_ROOT 기준 경로> | 신규 / 갱신 / 상태 변경 | <변경 내용 한 줄> | <변경 후 문서 상태> |`
3. 같은 날짜·같은 경로·같은 내용 줄이 이미 있으면 추가하지 않는다. 기존 줄은 고치지 않는다(정정은 새 줄).
4. 오탈자 수준 수정, 반영하지 않은 B·C 작업은 적지 않는다.

## 12단계. 마무리 확인

- 반영한 파일을 다시 Read 해 비밀값·내부 절대 경로(개인 PC 경로는 필요한 경우만)·추측 표현이 없는지 본다.
- 프로젝트 작업 폴더의 파일은 이 skill 로 바꾸지 않았는지 확인한다(`config.local.json` 제외).

## 13단계. 결과 보고 (국문)

```
## 매뉴얼 반영 결과 (<날짜>, MANUAL_ROOT=<경로>)

### 반영 완료
| 구분 | 문서 경로 | 주요 반영 내용 | 문서 상태 |
|---|---|---|---|
| 신규 / 갱신 | 03_Control_Platform/… .md | … | 초안 / 검증 중 … |

### 반영 제외
| 작업 | 제외 사유(C 기준) |

### 검토 필요
| # | 작업·내용 | 이유 | 권장안 |
(분류 모호·검증 안 된 정보·충돌·구조 변경 필요·추가 확인 필요)

### 관리 문서
- README: 갱신함(추가 N줄·상태 변경 N줄) / 안 함(사유)
- MANUAL_LOG: 갱신함(N줄) / 안 함(사유)

### 변경 파일
- <MANUAL_ROOT 기준 경로 목록>  (dry-run 이면 "없음 — 계획만")
```

- 문서화 대상이 하나도 없으면 그렇다고 짧게 알리고 파일을 쓰지 않는다.
- 검증을 못 한 것은 무엇을 왜 못 했는지 적는다.

## 경로 설정 파일

- `config.local.json` (이 폴더, Git 추적 제외): `{"manual_root": "<절대 경로>"}`. 형식은 `config.example.json`.
- 다른 PC 에서는 `TOOL set-root <경로>` 한 번, 또는 환경 변수 `M20_MANUAL_ROOT`.
- 매뉴얼 저장소가 프로젝트 밖이면 Claude Code 파일 접근을 위해 `.claude/settings.local.json` 의 `permissions.additionalDirectories` 에 같은 경로를 넣는다(이 파일도 Git 추적 제외).
